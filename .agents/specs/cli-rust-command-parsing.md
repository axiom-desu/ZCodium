# CLI Rust command parsing

## Contract and owner

`apps/zcode-cli-rust/crates/protocol` is the sole owner of command-envelope parsing and normalization. Its public `parse_command(&Value) -> Result<Command, String>` is the only validation/DTO construction path. `validate_command` is compatibility-only and delegates to `parse_command`, discarding the DTO; core command admission consumes the parsed DTO and never deserializes business data directly from the raw JSON. Raw input may remain available only for telemetry (including TTFT).

The parser models current TypeScript `parseCommandEnvelope`/Zod behavior: normalize known trim-transform strings, validate strictness and cross-field refinements without dropping unknown fields, then strip unknown keys and apply Zod defaults, finally construct the canonical DTO. ACK behavior remains the existing invalid-payload ACK for parse failure and normal admission/ACK behavior for success.

## Normalization and transform support

The maintained trim-path allowlist is an explicit manual semantic registration, checked against a recursive inventory of the actual Zod internal schema tree. This inventory only recognizes a single string overwrite at manually registered known paths as the trim behavior; it cannot statically identify arbitrary transaction/transform functions from callback source. Inventory retains every actual string-overwrite leaf, including multiple union branches at one path; it does not de-duplicate leaves by path. A leaf must be a string schema with exactly one overwrite, and cycle detection only prevents recursion loops. Zod is pinned to 4.6.5; generator execution fails on a version mismatch, unknown transform/pipe, unlisted trim path, stale allowlist entry, duplicate overwrite, malformed/unknown checks, or other unrepresentable schema construct. Inventory traverses arrays, optionals, unions, and records. Only `x-zcode-trim: true` is supported; explicit false and non-boolean values fail closed. The 350 TypeScript oracle samples are finite regression coverage, not proof that arbitrary transform functions have been identified or proven.

Trim paths: envelope `baseLogEpoch`; `modelSelection.providerId`, `.modelId`, `.options.reasoningLevel`; MCP `name`, `command`, `env[].name`, `headers[].name`, and OAuth client fields; `sideSession.firstInput.text`; `sendText.currentUrl`, `context_refs[].context_id`, and `botDeliveryTarget` identifiers; `row.target.entityId`; workspace-hook targets/review identifiers; and `discardSharedContext.contextId`. In particular, `sendText.text` is not trimmed. The generated JSON Schema marks these strings with `x-zcode-trim: true`. The Rust schema implementation applies JavaScript `String.prototype.trim` whitespace semantics (including U+FEFF and NBSP); it does not substitute Rust's whitespace trim. For unions, normalized candidates are validated as actual alternatives rather than applying an order-dependent global mutation.

The generated per-leaf fixture has 63 unique manually registered paths, 70 actual leaf branches, and 350 TypeScript Zod cases (five representative raw strings per leaf). Each expected result is produced by that actual leaf's `safeParse`; each serialized schema is generated with `toSchema(leaf)` only after that schema object has been authorized by the inventory. Rust's `protocol/tests/trim_oracle.rs` compiles each leaf schema with public `zcode_cli_schema::Node`, then exercises normalize → validate → strip only on success and compares complete expected parsed values. The 350 cases are an oracle for those recorded inputs only, not proof that arbitrary transform callbacks have been recognized or that all possible inputs are equivalent. Unknown transforms and malformed recognized schema constraints fail closed; no fallback to `{}` is permitted.

## DTO and serialization

`baseRevision` follows the TypeScript `z.number().optional()` contract and is represented as `Option<f64>`: negative, fractional, and integral finite JSON numbers parse. Core stale-revision comparison uses numeric semantics and fork/side-chat fallback is `0.0`; the parser does not silently impose a nonnegative integer restriction. Optional `ttft`, `baseRevision`, and `baseLogEpoch` are omitted when absent during serialization. `sessionId: None` remains serialized as `null`.

## Verification scenarios

TypeScript-oracle fixtures compare complete successful parsed outputs, including stripping unknown nested keys and applying defaults. The generated command oracle contains 29 command cases and one ACK case; existing Rust protocol tests consume it and compare complete DTOs without deleting keys or post-processing away null fields. It covers null/absent baseLogEpoch, side-session firstInput trimming, sendText text preservation alongside model/browser/context fields, createSession MCP stdio/HTTP union branches with OAuth and stripping, and workspace-hook review identifiers. The separate generated trim oracle exercises all 70 recorded leaf branches across five representative inputs apiece. Node support tests cover stale/unlisted allowlist entries, duplicate overwrites, unknown schema/transform/check kinds, and invalid explicit trim-extension values. The bounded samples do not prove the transform for arbitrary inputs. This contract covers only the enumerated Zod subset and semantic registrations, not arbitrary Zod schemas or overwrite behavior.
